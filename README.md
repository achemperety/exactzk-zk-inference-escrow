# ExactZK zk-inference-escrow

Payment for a machine-learning inference that is released only by a zero-knowledge proof that a stated circuit maps the payer's committed input to the output delivered. No valid proof, no payment; a payment never proven goes back to the payer after its deadline. This repository is version 3 of the settlement contracts, with a draft x402 specification of the proof as a condition on `auth-capture` and `batch-settlement`, a client, server middleware and a Base Sepolia deployment.

**Status: testnet only, unaudited.** See [SECURITY.md](SECURITY.md) and [Known limitations](#known-limitations).

## What it is

- **Contracts** (`src/`): a verifier registry with no owner, whose entries are identified by their content; one interface for proof systems (`IProofVerifier`) and an adapter for EZKL-generated Halo2 verifiers; `SoloSettlement` (one payment per proof, in one transaction or through a lock); `ChannelSettlement` (prepaid channels, one proof settles a batch of requests); an ERC-8183 evaluator and an ERC-8004 validator that act on proofs; for x402's `auth-capture` escrow, an operator that pays out only against a proof (`AuthCaptureProofOperator`) and a read-only proof policy whose check returns a reason, not a boolean (`ProofCapturePolicy`, with `PolicyCaptureOperator`).
- **A draft x402 specification**, shape (a) of [x402#4390](https://github.com/x402-foundation/x402/issues/4390): the [proof condition](specs/schemes/proof-gated/proof_condition.md), a [policy profile for `auth-capture`](specs/schemes/proof-gated/auth_capture_policy_evm.md), a [claim-condition proposal for `batch-settlement`](specs/schemes/proof-gated/batch_settlement_claim_evm.md) with a prototype gate, the [reference implementation and gas baseline](specs/schemes/proof-gated/reference_evm.md), and a [review list](specs/schemes/proof-gated/REVIEW.md) of every requirement and number with its source.
- **Clients**: a TypeScript client that checks an offer before it signs (`clients/ts`), Python server middleware with a `prove()` callback (`clients/python`), and a one-command quickstart against the testnet deployment.
- **Measurements**: every gas, time and memory figure, with the machine, method and source of each, in [MEASUREMENTS.md](MEASUREMENTS.md).

## What it is not

- **Not evidence that a model is good, or that it is the model you meant.** A proof shows that the circuit behind a registry entry maps the committed input to the output. Which model an entry stands for is checked off-chain (`scripts/verify_entry.py`), and the circuit is a fixed-point quantisation of the model.
- **Not private inference.** The chain sees a commitment to the input, but the server that proves sees the input itself.
- **Not a prover.** Proving runs on the server, with EZKL. The tests and the quickstart use stored proofs.
- **Not accepted by x402.** The specification is a draft for discussion with the x402 maintainers.
- **Not for value.** Testnet only, unaudited, with a reference string generated by a single party.

## Quickstart

Pay the Base Sepolia deployment for one proof-checked inference. One command; it needs Node 20 or later and git, and nothing is proved on your machine.

```
git clone https://github.com/achemperety/exactzk-zk-inference-escrow
cd exactzk-zk-inference-escrow
bash quickstart.sh
```

It creates a throwaway testnet key in `.quickstart/key`, prints its address, and waits until you have sent it at least 0.01 USDC ([Circle's faucet](https://faucet.circle.com), Base Sepolia) and 0.0001 ETH (any faucet on [this list](https://docs.base.org/chain/network-faucets)). It then pays 0.01 USDC through `SoloSettlement` in one transaction, released only by a valid proof from the registered solo verifier for the published input, and prints the settlement transaction, the model's output as read from the contract's event, and the outcome:

```
Outcome: settled
  settlement transaction: 0x7387e2b5… (block 62983372, 783326 gas)
  output (10 logits, fixed point 2^-13): 0.080 -0.207 0.125 0.103 0.112 -0.011 -0.068 0.044 -0.229 -0.225
  the model's answer: digit 2
```

**Timed on a clean machine, 2026-11-24.** A new Linux user on 2 vCPUs of an Intel Xeon Gold 5220R (Ubuntu 24.04), with Node 24.22.3 and git 2.43 and nothing else, ran `time` over the clone and `bash quickstart.sh`: 6 min 25.4 s in all, of which 6 min 16.3 s was spent waiting for the faucet funds to arrive. Everything else took 9.1 s: the clone, installing 17 packages (6 s), and the payment, from funded to the settled transaction (2.1 s). The run peaked at 439 MB of memory, page cache included. The repository was not public yet, so that run cloned a copy of it rather than GitHub.

Before you pay, the quickstart checks that the stored proof is the one [circuits/spike-mlp/MANIFEST.md](circuits/spike-mlp/MANIFEST.md) pins, that the registered verifier and adapter run the code their entry names, and that the settlement contract computes the same request id as the client. Live mode, `bash quickstart.sh live <prover url> <input.json>`, buys an inference of your own input from a running prover instead (an x402 server built with [clients/python](clients/python/README.md)); see [clients/ts](clients/ts/README.md).

### Check a registry entry against the published model

```
bash scripts/fetch_srs.sh
python3 scripts/verify_entry.py solo
```

From the model file, the pinned `settings.json` and the SRS (each checked against its SHA-256), this regenerates the verifying key and the verifier, compiles it with solc 0.8.20, and compares the result with the registry entry on Base Sepolia: key hash, code hash, code without its metadata trailer, and the entry's id. It only reads the chain. It needs Python and EZKL 23.0.5. On 2 vCPUs of an Intel Xeon Gold 5220R the solo entry matched in 21.7 s at 996 MB peak, most of it the key setup; `--from-vk` starts from the published key, needs no model weights, and took 3.6 s (solo) and 8.1 s (K=8). The K=8 key setup needs about 6.4 GB and was not run there ([measurements/2026-11-24-verify-entry/](measurements/2026-11-24-verify-entry/README.md)).

## Known limitations

In plain words:

- **Nothing here has been audited, and it runs on a testnet only.** Do not use it for anything of value.
- **The chain checks code, not models.** A registry entry pins a verifier's bytecode. Whether that bytecode comes from the model you have in mind is checked off-chain, by regenerating it from the published files, and whose model it is has to be said, and signed, by whoever publishes the model.
- **The model in the proof is a rounded copy.** The circuit computes with fixed-point numbers (scale 2^13), so its outputs are those of a quantised model, not of the original floating-point one.
- **x402's own `auth-capture` client gets escrow safety only.** On the terms-authorizer route it signs whatever terms the server binds, so it is protected on amount, recipient and refund, but only a client that checks the binding knows a capture needs a proof of the terms it meant to buy. The proof policy binds the terms through the salt nonce, which x402's client draws at random, so that client cannot pay through the policy at all: its hold returns to it after the deadline.
- **The input commitment needs fresh randomness from the client**, drawn after the server has named the verifier. Without it, a server could search for two sets of terms that bind to the same payment (about 2^80 work instead of 2^160). The quickstart's published-proof mode has none: it shows the payment path, not a private purchase.
- **A proof is not tied to one request.** A proof for a verifier and an input commitment settles any request naming both; unique commitments come from the client's randomness.
- **Proving is slow and memory-hungry.** One solo proof takes about 20 s on 2 vCPUs of an Intel Xeon Gold 5220R; a K=8 proof needs about 12.8 GB. The largest model measured has 52,650 parameters.
- **Verification is most of the cost.** About 577,000 of the roughly 770,000 gas of a solo payment is the generated Halo2 verifier.
- **The reference string is a single party's.** The circuits' KZG parameters were generated locally, not in a public ceremony.
- **The Groth16 version is a prototype.** Its setup is insecure (single party), and it commits to the input differently, so it does not prove the same statement.
- **No facilitator.** The reference server settles on chain itself; the facilitator parts of the specification are not implemented.
- **The ERCs are drafts.** The evaluator and the validator were tested against each ERC's reference code at pinned commits; where text and code differ is in [docs/erc-text-vs-code.md](docs/erc-text-vs-code.md).

## Same circuits, new settlement contracts, new addresses

- **Same circuits.** The two pinned circuits, their verifying keys and their verifier bytecode are byte-identical to the ones used before version 3. A circuit's identity is its model files, its pinned `settings.json` and its SRS: settings regenerated from the same model can give another key. Their hashes are in [circuits/spike-mlp/MANIFEST.md](circuits/spike-mlp/MANIFEST.md), and every carried-over file is listed with its SHA-256 in [provenance/](provenance/README.md).
- **New settlement contracts**, written from scratch in `src/`.
- **New addresses.** Version 3 is deployed on Base Sepolia from a fresh testnet-only account, by `script/DeployBaseSepolia.s.sol` from the sources in this repository ([docs/deployment-notes.md](docs/deployment-notes.md)); the addresses are in [deployments/base-sepolia.json](deployments/base-sepolia.json), and `scripts/check_deployment.py` checks them against the chain. A verifier is identified by key hash and code hash, not by address, so the same circuit has the same identifier wherever the same bytecode is deployed.

## How a channel closes

The payer asks (`requestClose`). For the channel's challenge window the provider may answer with the latest voucher it holds and has not settled (`challengeClose`); its cumulative amount, less what has settled since, is held for the provider. After the window anyone can finalize (`finalizeClose`): everything not held goes back to the payer at once. The provider then has the channel's prove window to settle the held vouchers; whatever is left after that, anyone can return to the payer (`sweepExpiredHold`). Vouchers settle throughout, and every settled voucher shrinks the hold. A provider that cannot prove a voucher gives it up with `waive`, so that the vouchers after it can still settle.

Each channel sets its own windows when it is opened; the contract only enforces minimums (60 seconds to prove, 300 seconds to challenge). Recommended defaults for clients:

| Window | Default | Why |
|---|---|---|
| Prove window | 10 minutes | Long enough to fill a batch and prove it, short enough that a hold ends soon after a close: held funds are free at the latest one prove window after the challenge window. |
| Challenge window | 24 hours | The provider has to notice a close request and answer it with its latest voucher; a window measured in hours, not minutes, survives a provider's outage or a congested chain without the payer taking back money for requests that were already served. |

## Proof-gated ERC-8183 jobs and ERC-8004 validations

**ERC-8183 (agentic commerce jobs).** `ProofEvaluator8183` is a job's evaluator. Before funding, the client names the terms with `setTerms`: the registry entry whose circuit must produce the proof and the commitment to the input. Once the provider has submitted, anyone may call `evaluate` with the output and a proof. A valid proof completes the job, with the claim's digest as the reason, and publishes the output in `Evaluated`. A proof that does not verify, or a verifier that cannot be run, reverts and leaves the job as it was: the evaluator never rejects a job, because anyone can submit a bad proof. Proofs are refused from the job's `expiredAt` on, when the job contract starts refunding. The provider can give a job up with `forfeit`, which refunds the client. If the job contract pays its evaluator a fee, the evaluator passes it to the provider in the same call; it keeps no job's funds, has no owner and charges nothing.

**A provider should read `terms(jobContract, jobId)` before starting work**, and check that the verifier and the input commitment are the ones it agreed to. The terms cannot change once set, and they can only be set while the job is Open. Without a hook the evaluator cannot see what the provider submitted, so a completed job means "a valid proof for the agreed circuit and input", not "the proven output equals the deliverable".

**ERC-8004 (validation registry).** `ProofValidator8004` answers validation requests with what a proof shows. The agent's owner or operator opens a request in the Validation Registry naming the validator, with the hash from `requestHashOf(agentId, verifierId, inputCommitment, claimedOutputHash, salt)`. Anyone may then call `respond` with the output and a proof; the validator answers only if the agent the registry recorded for the request is the agent its hash commits to. A valid proof of the claimed output is answered 100, tag `zk-proof/passed`. A valid proof of a different output is answered 0, tag `zk-proof/contradicted`. Nothing else is ever written: an invalid proof or a verifier that cannot be run reverts, and a request nobody proves stays unanswered, so the registry's averages count only what proofs established. A proof does not name an agent: "passed" says that the claimed output is what the circuit gives for that input, not who computed it.

**What these were tested against.** Both ERCs are drafts, so the tests use their reference contracts, built here from source:

The evaluator relies on the reference job contract's `getJob`, which the ERC's text does not specify.

## x402: the auth-capture routes and the native wire format

`x402/` holds a minimal x402 version 2 server and clients for one proof-gated inference, run end to end on a local node with the stored proof. Two ways to pay are offered:

- **`proof-gated`**, the native contracts' own wire format: the payer signs one ERC-3009 authorization whose nonce is `SoloSettlement`'s request id, in the `authorization` flow (one transaction) or the `escrow` flow (lock, then release). It was the first draft's dedicated scheme; the specification no longer proposes it for x402 and keeps the contracts as the [reference implementation and gas baseline](specs/schemes/proof-gated/reference_evm.md).
- **x402's own `auth-capture`**, with `AuthCaptureProofOperator` as a `"custom"` operator. The server publishes the terms (verifier id and input commitment) as `extra.receiverAuthorizer`, an address derived from them. x402's own client, unmodified, binds that into the payment's salt, so the payer's signature commits to the terms. The hold is captured only with a valid proof for them, the receiver can give it back early, and otherwise the payer reclaims it after the capture deadline.

A proof that does not verify and a verifier that cannot be run reach the client as two distinct `errorReason` values, `invalid_auth_capture_evm_proof_invalid` and `invalid_auth_capture_evm_verifier_unavailable`. These are the names the specification gives them ([error codes](specs/schemes/proof-gated/reference_evm.md#error-codes)). Every `PaymentRequired`, `PaymentPayload` and `SettleResponse` is checked against x402's own schemas and types at a pinned commit.

The [policy profile](specs/schemes/proof-gated/auth_capture_policy_evm.md) is the shape the specification now proposes for `auth-capture`: a read-only policy (`ProofCapturePolicy`) whose check answers `Authorized`, `ProofInvalid`, `VerifierUnavailable` or `Denied`, so an invalid proof and one that cannot be checked stay two outcomes. It runs today through a `"custom"` operator fixed to it (`PolicyCaptureOperator`), tested against the escrow built from source; it is not deployed and not yet wired into the x402 run.

Paying through x402's escrow costs about 50,000 gas more than the native escrow flow and about 65,000 more than the native one-transaction flow; the proof check is identical, and the difference is the escrow's own bookkeeping and its extra token hop ([measurements/2026-11-24-x402-auth-capture/](measurements/2026-11-24-x402-auth-capture/README.md)).

## Build and test

Requires [Foundry](https://getfoundry.sh). OpenZeppelin Contracts (v5.7.0, for its signature helpers and safe token transfers) and forge-std come in as pinned submodules; so do the ERC-8004 reference registries, OpenZeppelin Contracts Upgradeable v5.4.0 and x402's auth-capture escrow, which only the tests use. No proving, key generation or model inference is needed: the tests use stored proofs.

Only three nested submodules are needed; a recursive clone also fetches large trees under commerce-payments that nothing here compiles.

```
git clone <this repository> && cd <its folder>
git submodule update --init
git -C lib/openzeppelin-contracts-upgradeable submodule update --init lib/openzeppelin-contracts
git -C lib/commerce-payments submodule update --init lib/solady lib/spend-permissions
git -C lib/commerce-payments/lib/spend-permissions submodule update --init lib/openzeppelin-contracts
forge build
forge test
bash scripts/hygiene_scan.sh
python3 scripts/test_verify_entry.py
```

The x402 end-to-end runs need Node and Python as well; see [x402/README.md](x402/README.md) and [clients/ts/README.md](clients/ts/README.md). How to contribute: [CONTRIBUTING.md](CONTRIBUTING.md).
